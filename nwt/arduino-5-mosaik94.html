Arrays, Interrupts und Troubleshooting

Vor dem Start

Weil du in echten Arduino-Projekten fast immer mehrere Dinge gleichzeitig brauchst: übersichtliche Datenstrukturen, schnelle Reaktionen auf Ereignisse und eine saubere Methode zur Fehlersuche. Genau diese Kombination trainierst du hier.

Arbeitsplatz und erster Upload

Für den Uno R3 wird in der IDE Arduino Uno aus dem Paket Arduino AVR Boards gewählt. Der Port ist der beim Anschließen tatsächlich neu erscheinende Anschluss; eine konkrete COM-Nummer ist rechnerabhängig. Überprüfen kompiliert, Hochladen überträgt zusätzlich auf das Board. Nach dem Upload von Blink blinkt die eingebaute L-LED. Ein Serieller Monitor muss auf dieselben 9600 Baud wie Serial.begin(9600) eingestellt werden; RESET startet auch eine Ausgabe aus setup() erneut. Vor jedem Umbau werden USB und weitere Versorgungen getrennt.

Sicherung: Wie funktionieren Arrays?

Ein Array ist eine geordnete Liste von Werten. Jeder Eintrag wird über einen Index angesprochen. Der erste Listenplatz hat die Nummer 0 . Im Melodie-Beispiel berechnet man die Tondauer aus dem Notenwert.

Wahr oder falsch?

Falsch. Das erste Element eines Arrays hat normalerweise den Index 1.

Falsch. Das erste Element einer Liste bekommt immer Index 0.

Versuchsprotokoll: Array-Aufgaben

Eine mögliche Antwort

Melodie und Indexgrenzen

Die folgenden Angaben sind aus dem Code abgeleitete Erwartungen, keine gemessenen Versuchsergebnisse. Bei 0.30 → 0.60 verdoppelt sich der berechnete Pausenfaktor; wegen der ganzzahligen Speicherung können einzelne Pausen nicht exakt doppelt so viele Millisekunden umfassen (bei 125 ms Ton: 37 statt 75 ms Pause). Frequenz und Tondauer bleiben gleich. Nach Wiederherstellen von 0.30 verdoppelt 1000 → 2000 die berechneten Tondauern und damit ungefähr auch die Pausen; die Tonhöhen bleiben gleich. In 6.1 entstehen 25 Ausgabezeilen mit den Indizes 0 bis 24. i <= 25 würde auch Index 25 lesen, der nicht existiert; das Verhalten wäre undefiniert. Lösche ich einen mittleren Notenwert, passen die späteren Paare nicht mehr zusammen und die Listenlängen unterscheiden sich. Im vorgegebenen Sketch stoppt dann static_assert bereits die Kompilierung; ohne diese Prüfung könnte am Ende außerhalb des Notenwert-Arrays gelesen werden.

Tafeldienst und Literaturautomat

Für die acht Startnamen sind nur Indizes 0 bis 7 möglich. Eine nur zur Veranschaulichung gewählte Folge von zehn zulässigen Ausgaben lautet: 0: Martin; 3: Kolja; 3: Kolja; 7: Rainer; 1: Volker; 5: Mario; 2: Frank; 0: Martin; 6: Peter; 4: Alexander. Das sind keine aufgezeichneten Ziehungen. Wiederholungen sind beim unabhängigen Ziehen erlaubt; gleiche Häufigkeiten in zehn Versuchen sind nicht vorgeschrieben. Nach einem neunten Namen wird der Bereich durch sizeof automatisch 0 bis 8. Im Literatur-Startcode gibt es 3 · 3 = 9 mögliche Kombinationen, zum Beispiel „Wer reitet so spät durch Nacht und Wind?“ und „Wer reitet so spät durch Nebel und Schnee?“. Eine eigene Variante nutzt x = {Idee, Frage, Antwort, Vermutung} und y = {Experiment, Modell, Beobachtung}. Zwei mögliche, nicht als real beobachtet behauptete Ausgaben sind „Heute trifft Idee auf Experiment.“ und „Heute trifft Frage auf Modell.“. Dafür werden anzahlX = 4 und anzahlY = 3 getrennt berechnet; es gibt 12 Kombinationen.

Hausdienste

Die Papierprobe beginnt mit {0,1,2}. Beim Tausch i = 2, j = 0 entsteht {2,1,0}; bei i = 1, j = 1 bleibt {2,1,0}. Damit bekommt Sam abwaschen, Robin aufräumen und Alex Staub wischen. Beim Test mit vier Personen und vier Diensten muss jede Verteilung vier Zeilen mit jedem Namen und jedem Dienst genau einmal enthalten. Eine mögliche Verteilung wäre Alex → abwaschen, Sam → aufräumen, Mia → Staub wischen, Robin → Müll trennen. Sie illustriert nur die Prüfbedingung. Jeder Tausch erhält alle vorhandenen Indizes genau einmal. Wiederholungen eines Dienstes über mehrere Wochen sind trotzdem möglich, weil keine frühere Zuteilung gespeichert oder ausgeschlossen wird.

Lautsprecher-Aufbau mit Vorwiderstand

Am Uno R3 führt D8 über 330 Ω zum geprüften kleinen passiven Lautsprecher und dessen zweiter Anschluss zu GND. Der Widerstand begrenzt den Strom und hält den Ton leise; 1 kΩ macht ihn noch leiser. Ein passiver Piezo ist eine Alternative. Bei unbekannten Bauteilen entscheidet die Bauteilprüfung, nicht eine vermutete Beschriftung. Der Tonaufbau bleibt beim Erweitern der Melodie bestehen und wird vor den reinen seriellen Aufgaben bei getrennter Versorgung entfernt.

Sechs Töne: Aufbau, Pause und Tempo

const byte lautsprecher = 8;
const int Melodie[] = {175,175,196,175,262,247};
const int notenWert[] = {8,8,4,4,4,2};
const int anzahlToene = sizeof(Melodie) / sizeof(Melodie[0]);
static_assert(anzahlToene == sizeof(notenWert) / sizeof(notenWert[0]),
              "Die beiden Listen muessen gleich lang sein.");

void setup() {
  Serial.begin(9600);
  for (int i = 0; i < anzahlToene; i++) {
    int tonDauer = 1000 / notenWert[i];
    Serial.print(i);
    Serial.print(": ");
    Serial.println(Melodie[i]);
    tone(lautsprecher, Melodie[i]);
    delay(tonDauer);
    noTone(lautsprecher);
    int pauseZwischenNoten = tonDauer * 0.30;
    delay(pauseZwischenNoten);
  }
}

void loop() {}

Der passive Piezo liegt zwischen D8 und GND; ein niederohmiger Lautsprecher braucht eine geprüfte Treiberschaltung. Die ersten beiden Töne haben dieselbe Frequenz 175 Hz. Der letzte Ton dauert mit Notenwert 2 am längsten: 1000 / 2 = 500 ms. Der Durchlauf erfolgt einmal in setup(), erneut nach RESET. Die Pausenänderung 0.30 → 0.60 verändert nur die Pausen; 1000 → 2000 verdoppelt die Tondauern bei gleichbleibenden Frequenzen. Ganzzahlige Pausenwerte können Rundungsabweichungen vom exakten Faktor zwei haben.

6.4 · Vier Hausdienste ohne Doppelbelegung

const char* namen[] = {"Alex", "Robin", "Sam", "Mia"};
const char* dienste[] = {"abwaschen", "aufräumen", "Staub wischen", "Müll trennen"};
const int anzahl = sizeof(namen) / sizeof(namen[0]);
static_assert(anzahl == sizeof(dienste) / sizeof(dienste[0]),
              "Gleich viele Personen und Dienste erforderlich.");
int reihenfolge[anzahl];

void setup() {
  Serial.begin(9600);
  randomSeed(analogRead(A0));
}

void loop() {
  for (int i = 0; i < anzahl; i++) reihenfolge[i] = i;
  for (int i = anzahl - 1; i > 0; i--) {
    int j = random(i + 1);
    int temp = reihenfolge[i];
    reihenfolge[i] = reihenfolge[j];
    reihenfolge[j] = temp;
  }
  Serial.println("Neue Verteilung:");
  for (int i = 0; i < anzahl; i++) {
    Serial.print(namen[reihenfolge[i]]);
    Serial.print(" darf ");
    Serial.println(dienste[i]);
  }
  Serial.println();
  delay(5000);
}

Fisher-Yates mischt die vollständige Indexliste mit gültigen Tauschindizes. In der dreielementigen Papierprobe entstehen {2,1,0} und nochmals {2,1,0}. Jede Person und jeder Dienst kommen pro Verteilung genau einmal vor. Auch eine unveränderte Reihenfolge ist ein gültiges Mischergebnis. Ein Wochenplan müsste zusätzlich bisherige Dienste speichern und bei der Zuteilung berücksichtigen.

Interrupt: Auf Ereignisse reagieren

Ablaufspur: Vom Tastendruck zur Reaktion

Ereignisaktiver Bereichzustandnächster Schritt
Normalbetriebloop()0Hauptprogramm läuft weiter
Signal wechselt von HIGH zu LOWISR1ISR wird beendet
ISR ist beendet; vor der Flag-Übernahmeloop()1Aktion ausführen

Ordne den Interrupt-Ablauf

  1. Am Taster ändert sich das Signal am Pin.
  2. Der Interrupt erkennt die Signaländerung.
  3. Das Hauptprogramm wird kurz unterbrochen.
  4. Die Interrupt Service Routine wird ausgeführt.
  5. Nach der ISR läuft das Hauptprogramm an der unterbrochenen Stelle weiter.

Was gehört in eine ISR, was nicht?

KategorieBegriff
In einer ISR sinnvollNur kurz einen Zustand merken
In einer ISR sinnvollEine Variable auf 1 setzen
In einer ISR vermeidendelay() benutzen
In einer ISR vermeidenSeriellen Monitor umfangreich benutzen
In einer ISR vermeidenLC-Display ansteuern
In einer ISR vermeidenAufwändige Berechnungen machen

Warum volatile?

zustand wird von der ISR geändert und von loop() gelesen und gelöscht. volatile sorgt dafür, dass der Compiler die vorgesehenen Speicherzugriffe beibehält und Änderungen durch die ISR sichtbar bleiben. gemerkt ist nur eine lokale Kopie im Hauptprogramm. volatile macht die Folge aus Lesen und Löschen nicht unteilbar; dafür sperrt holeEreignis() kurz die Interrupts.

Wahr oder falsch?

Falsch. Während einer ISR sind delay(), serieller Monitor und aufwändige Berechnungen gute Ideen, weil der Interrupt dann besonders viel erledigt.

Falsch. Eine ISR muss kurz gehalten werden. delay(), serieller Monitor, LC-Display und aufwändige Berechnungen sollen dort nicht benutzt werden.

Transfer: Interrupt sinnvoll beschreiben

Eine mögliche Antwort

Beim Polling wird der Eingang nur an bestimmten Stellen gelesen; ein kurzer Tastendruck zwischen zwei Abfragen kann unbemerkt bleiben. Ein Interrupt kann die fallende Flanke auch während delay() erfassen und die kurze ISR aufrufen. Die ISR setzt den gemeinsamen volatile-Merker, dessen Änderungen im Hauptprogramm sichtbar bleiben müssen. loop() übernimmt und löscht den Merker bei kurz gesperrten Interrupts, damit die ISR nicht zwischen diesen beiden Zugriffen ein neues Ereignis eintragen kann, das gleich wieder gelöscht würde. Die Aktion beginnt im Merker-Sketch erst nach dem laufenden 500-ms-Schritt und kann das Lauflicht zusätzlich verzögern. Ein einzelnes Flag merkt nur mindestens eine Flanke, zählt keine mehreren Ereignisse und entprellt den Taster nicht.

Versuchsprotokoll: Drei Arten der Tasterabfrage

Eine mögliche Antwort

Direkte ISR und Polling

Der Taster verbindet D2 mit GND. Das Lauflicht verwendet D4 bis D11, die rote LED D12; alle neun LEDs besitzen je 330 Ω in Reihe. Ein Umlauf ohne Zusatzaktion dauert ungefähr 8 · 500 ms = 4 s plus Ausführungszeit der Anweisungen. Erwartetes Verhalten: Die direkte ISR schaltet D12 bei einer FALLING-Flanke schon innerhalb eines Lauflichtschritts ein, während die Polling-Kopie den Pegel nur am Umlaufanfang liest. Ein kurzer Druck zwischen zwei Polling-Abfragen bleibt dort unbemerkt; ein über einen Abfragezeitpunkt hinaus gehaltener Taster wird erkannt. D12 wird bei beiden Versionen am Umlaufende ausgeschaltet. Bei einem weiter gehaltenen Taster schaltet die Polling-Kopie D12 zu Beginn des nächsten Umlaufs wieder ein; die FALLING-Version braucht eine neue fallende Flanke. Eine sehr kurze rote Leuchtphase am Umlaufende ist möglich. Das sind erwartete Abläufe, keine behaupteten Hardwarebeobachtungen.

Merker und eigene Aktion

void machIrgendwas() {
  for (byte k = 0; k < 3; k++) {
    digitalWrite(rot, HIGH);
    delay(100);
    digitalWrite(rot, LOW);
    delay(100);
  }

Die drei Blinkimpulse dauern zusammen etwa 600 ms und werden in loop() ausgeführt. Eine eigene Idee wären zwei längere Blinkimpulse mit 400 ms an und 200 ms aus; dafür ändere ich nur machIrgendwas():

void machIrgendwas() {
  for (byte k = 0; k < 2; k++) {
    digitalWrite(rot, HIGH);
    delay(400);
    digitalWrite(rot, LOW);
    delay(200);
  }
}

Beim Merker-Sketch wird die Flanke während delay(500) erfasst, die Aktion beginnt erst nach Ende des laufenden Schritts. Während der Aktion stehen alle Lauflicht-LEDs still und sind aus, weil der aktuelle Ausgang zuvor gelöscht wurde und der nächste noch nicht gesetzt ist. Neue Flanken können während der Aktion das bereits übernommene Flag erneut setzen und eine spätere Aktion auslösen. Mehrere Flanken vor dem nächsten Übernehmen fallen jedoch zusammen; Tasterprellen kann unerwünschte weitere Flanken verursachen. Deshalb folgt keine feste Anzahl von Aktionen aus der Anzahl mechanischer Tastendrücke.

Lauflicht mit direkter ISR und Polling-Vergleich

const byte leds[] = {4,5,6,7,8,9,10,11};
const byte rot = 12;
const byte taster = 2;

void roteLed() {
  digitalWrite(rot, HIGH);
}

void setup() {
  for (byte i = 0; i < 8; i++) pinMode(leds[i], OUTPUT);
  pinMode(rot, OUTPUT);
  pinMode(taster, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(taster), roteLed, FALLING);
}

void loop() {
  for (byte i = 0; i < 8; i++) {
    digitalWrite(leds[i], HIGH);
    delay(500);
    digitalWrite(leds[i], LOW);
  }
  digitalWrite(rot, LOW);
}

D4 bis D11 steuern die acht Lauflicht-LEDs, D12 die rote LED; jeweils führt ein eigener 330-Ω-Widerstand zur Anode, die Kathode an GND. Der Taster verbindet D2 mit GND und wird als INPUT_PULLUP gelesen: offen HIGH, gedrückt LOW. FALLING erfasst den Tastendruck. Eine sehr kurze ISR darf hier direkt einen Ausgang setzen. Die rote LED geht am Umlaufende aus; ein Umlauf dauert ungefähr vier Sekunden. Die Polling-Kopie entfernt attachInterrupt und liest mit if (digitalRead(taster) == LOW) roteLed(); nur am Anfang von loop(). Sie verpasst kurze Drücke zwischen den Abfragen, kann aber einen dauerhaft gehaltenen Taster wiederholt erkennen. RISING reagiert beim Loslassen, CHANGE auf beide Flanken und LOW pegelabhängig wiederholt.

Ereignis merken und drei Blinkimpulse ausführen

const byte leds[] = {4,5,6,7,8,9,10,11};
const byte rot = 12;
const byte taster = 2;
volatile byte zustand = 0;

void meineISR() {
  zustand = 1;
}

byte holeEreignis() {
  // Nur aus loop() mit zuvor aktiven Interrupts aufrufen.
  noInterrupts();
  byte gemerkt = zustand;
  zustand = 0;
  interrupts();
  return gemerkt;
}

void machIrgendwas() {
  for (byte k = 0; k < 3; k++) {
    digitalWrite(rot, HIGH);
    delay(100);
    digitalWrite(rot, LOW);
    delay(100);
  }
}

void setup() {
  for (byte i = 0; i < 8; i++) pinMode(leds[i], OUTPUT);
  pinMode(rot, OUTPUT);
  pinMode(taster, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(taster), meineISR, FALLING);
}

void loop() {
  for (byte i = 0; i < 8; i++) {
    digitalWrite(leds[i], HIGH);
    delay(500);
    digitalWrite(leds[i], LOW);
    byte ausloesen = holeEreignis();
    if (ausloesen == 1) machIrgendwas();
  }
}

Die ISR setzt ausschließlich zustand = 1. holeEreignis() wird nur aus loop() mit eingeschalteten Interrupts aufgerufen und übernimmt und löscht den Merker bei kurz gesperrten Interrupts. Erst danach folgt die etwa 600-ms-Aktion. Eine Flanke während delay(500) wird vorher erfasst, aber erst am nächsten Prüfpunkt verarbeitet. Während der Aktion bleibt das Lauflicht stehen. Spätere Ereignisse können für den nächsten Prüfpunkt gespeichert werden; mehrere Flanken werden vom Flag zusammengefasst. Tasterprellen wird damit nicht beseitigt.

Warum wird bei if (sensorWert > 500); { Serial.println("A"); } auch für sensorWert = 400 ein A ausgegeben?

Das Semikolon ist die leere if-Anweisung; der nachfolgende Block läuft unabhängig von der Bedingung.

Die Bedingung steuert nur die leere Anweisung vor dem Semikolon. Der folgende Block gehört nicht mehr zum if und wird ausgeführt, auch wenn die Bedingung falsch ist.

Fehlermeldung einordnen

Prüfe nun die Upload-Meldung, die passende Boardauswahl, den tatsächlich angeschlossenen Port und das USB-Datenkabel. Beim normalen USB-Upload des Uno R3 ist die Programmer-Auswahl nicht der übliche Ansatz; sie gehört zum ausdrücklich gewählten Hochladen mit Programmer oder zum Bootloader-Schreiben.

Versuchsprotokoll: Fehler gezielt eingrenzen

Eine mögliche Antwort

Logik- und Compilerfehler

Die erwarteten Ausgaben sind vollständig durch die Testwerte bestimmt: Mit dem zusätzlichen if-Semikolon erscheint für 400 ebenso wie für 600 die jeweilige Zeile „Testwert: …“, dann „Zweig A: Wert ist groesser als 500“ und dann „Testende“. Ohne dieses Semikolon fehlt die Zweig-A-Zeile bei 400, bei 600 bleibt sie erhalten. Für 500 ist > 500 falsch und >= 500 wahr. Ein erfolgreicher Upload bestätigt die Übertragung, nicht die fachliche Aussage der Ausgabe.

Beim Entfernen des Semikolons hinter der Deklaration ist etwa eine Meldung wie „expected ',' or ';' before 'Serial'“ an der folgenden Serial-Zeile möglich; die konkrete Meldung ist compilerabhängig und kein hier aufgezeichnetes Versuchsergebnis. Die Ursache liegt in der vorherigen Zeile, die mit einem Semikolon ergänzt werden muss. exit status 1 meldet nur das Scheitern des Vorgangs, nicht die konkrete Ursache. Beim Zusatz-Semikolon nach if wird dagegen eine gültige leere Anweisung kompiliert; der folgende Block ist unabhängig. Ein = in einer Bedingung würde zuweisen, == vergleicht. Eine in loop() immer neu auf 0 gesetzte lokale Variable behält ihren Zählerstand nicht über Durchläufe.

Hardware und Weiterdenken

Erwartung beim nackten Uno R3 mit dem unveränderten Blink-Beispiel: Die eingebaute L-LED blinkt ungefähr im Sekundentakt. Ist das erfüllt, funktionieren die grundlegende Versorgung, Kompilierung und Übertragung für diesen Test. Eine einzelne externe dunkle LED prüfe ich bei getrennter Versorgung auf den richtigen Pin, Reihenschaltung mit 330 Ω, Polung, Breadboard-Reihe und GND; danach teste ich genau diesen Pin mit einer passenden Blink-Kopie. Ein mögliches eigenes Fehlerbeispiel wäre die logisch falsche Bedingung wert < 500 statt wert > 500: Der Sketch kompiliert und wird hochgeladen, wählt aber den falschen Zweig. Eine Ausgabe des Werts direkt vor der Bedingung und der Zweigname danach zeigen, ob Eingangswert oder Entscheidung falsch ist. Im Vergleich zum bloßen Vermuten kann ich so eine konkrete Fehlerursache prüfen. Ein nicht ausgeführter Hardwaretest wird als solcher gekennzeichnet.

Fehlerlabor: Reparierter vollständiger Sketch

void setup() {
  Serial.begin(9600);
  int sensorWert = 400;
  Serial.print("Testwert: ");
  Serial.println(sensorWert);
  if (sensorWert > 500)
  {
    Serial.println("Zweig A: Wert ist groesser als 500");
  }
  Serial.println("Testende");
}

void loop() {}

Mit dem vorgegebenen Testwert 400 entstehen nur „Testwert: 400“ und „Testende“. Für 600 kommt die Zweig-A-Zeile dazwischen. Bei 500 führt > nicht in Zweig A, >= dagegen schon. Das zusätzliche Semikolon nach if ist eine leere Anweisung, sodass der folgende eigenständige Block ohne Bedingung ausgeführt wird. Beim absichtlichen Entfernen des Deklarations-Semikolons wird der Compilerfehler durch Wiedereinsetzen behoben. Eine Compilerdiagnose kann erst die folgende Zeile markieren; exit status 1 ist lediglich der Fehlerstatus. Bei einer leeren for-Schleife folgt der separate Block einmal nach Schleifenende, bei einer leeren while-Schleife erst nach Ende des Wartens oder bei dauerhaft wahrer Bedingung gar nicht.
