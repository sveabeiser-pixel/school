Gruppe A: Vom Sensor zur Homepage

Wie kannst du nachweisen, dass die Temperatur auf der Homepage wirklich vom Sensor stammt und nicht aus einem alten Test? Verfolge einen Messwert von Station zu Station. Teste erst lokal, bevor du Geräte oder Dienste verbindest.

  1. Sensoren am ESP32 messen und seriell anzeigen
  2. ESP32 mit dem freigegebenen Schulnetz verbinden
  3. Auf dem Raspberry Pi eine Flask-API programmieren
  4. Messwerte per HTTP senden
  5. Messwerte in einer CSV-Datei speichern
  6. Temperatur mit Python als Diagramm darstellen
  7. Bei Bedarf auf SQLite umsteigen
  8. Letzten Messwert an den öffentlichen Webserver übertragen

Erst messen, dann vernetzen

Für den klassischen ESP32 nutzt du den KY-015 / DHT11 an GPIO4 und den KY-018 / LDR an GPIO34 (ADC1). Prüfe die Pinbelegung deines Boards und die Beschriftung der Module. Verbinde die Masseleitungen und halte das Analogsignal im 3,3-V-Bereich. In der ESP32-Anleitung findest du Hinweise zu Board, Port und Upload.

Installiere in der Arduino IDE die Bibliothek DHT sensor library von Adafruit mit ihren Abhängigkeiten. Öffne messstation.ino im gleichnamigen Sketch-Ordner. Lass WLAN_AKTIV und SENDEN zunächst auf false. Lade den Sketch hoch und öffne den seriellen Monitor bei 115200 Baud. Der Sketch liest alle fünf Sekunden aus.

Den ESP32 mit dem Schulnetz verbinden

Nutze ausschließlich ein von der Schul-IT freigegebenes Netz für Projektgeräte. Der Sketch ist für ein kompatibles 2,4-GHz-WLAN mit Netzname und gemeinsamem Kennwort gedacht. Bei Anmeldeportal, persönlichen WLAN-Konten oder voneinander getrennten Clients klärst du den Aufbau mit der Schul-IT, statt die Beschränkung zu umgehen.

Setze WLAN_AKTIV auf true, trage Netzname und Kennwort nur in deiner lokalen Sketch-Kopie ein und lass SENDEN auf false. Speichere keine Zugangsdaten im Repository, im Protokoll oder in Screenshots. Kontrolliere nach dem Hochladen die Meldung WLAN verbunden und die zugewiesene IP-Adresse im Monitor. Die Messung läuft auch ohne WLAN weiter.

Auf dem Raspberry Pi erhältst du mit hostname -I die IP-Adressen. Kläre, welche Adresse zum Projektnetz gehört. Die ESP32-Adresse zeigt, wo der Sender ist; in die spätere Ziel-URL kommt die Pi-Adresse. In WLAN, IP und HTTP findest du die Begriffe; dort spielt der ESP32 in einem anderen Versuch die Serverrolle.

Auf dem Raspberry Pi eine API programmieren

Der Pi ist der Server. Eine Route legt fest, was der Pi zu einer HTTP-Anfrage zurückgibt. GET fragt Daten ab; POST liefert hier einen neuen Datensatz. Programmiere und teste zuerst eine Route ohne Sensor und ohne Datei.

Erste Route: GET /api/health

Kopiere den Ordner material/gruppe-a auf den Pi oder lade die Dateien über die Links der Kapitel herunter. Installiere die Pakete in einer virtuellen Umgebung. Starte den ersten Versuch nur auf dem Pi:

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

Schreibe diesen Einstieg in api_uebung.py:

from flask import Flask

app = Flask(__name__)

@app.get("/api/health")
def health():
    return {"status": "ok"}

Starte die Anwendung mit flask --app api_uebung run und rufe curl -i http://127.0.0.1:5000/api/health in einem zweiten Terminal auf. Ergänze danach selbst eine Route /api/version, die eine Versionsnummer als JSON ausgibt. Vergleiche beide Antworten mit einem absichtlich falschen Pfad.

Vom Test zur Sensor-API

Entwirf nun den Ablauf für einen POST: JSON lesen, Werte prüfen, Empfangszeit hinzufügen, speichern und antworten. Verwende anschließend sensor_api.py mit messwerte.py als Referenz für deinen Entwurf. Das Abhängigkeitsverzeichnis enthält die Python-Pakete für den gesamten Messweg.

Messwerte senden und als CSV speichern

Der ESP32 sendet Temperatur in °C, relative Feuchte in Prozent und den ADC-Rohwert als Zahlen. Der Pi ergänzt received_at_utc: den Empfangszeitpunkt in UTC, nicht die Laufzeit seit dem ESP32-Start. Prüfe vorher die Uhr des Pi. Ungültige Messwerte kommen nicht in die Datei.

Zuerst mit Testdaten

Beende den Übungsserver. Starte flask --app sensor_api run im Materialordner und sende vom Pi selbst einen ausdrücklich fiktiven Datensatz:

curl -i -X POST http://127.0.0.1:5000/api/messwerte \
  -H 'Content-Type: application/json' \
  -d '{"temperature_c":21.5,"humidity_pct":53.0,"light_raw":1470}'
curl -i http://127.0.0.1:5000/api/aktuell

Bei Erfolg liefert POST 201 Created. tail -n 5 ~/.smart-coop/messwerte.csv zeigt die gespeicherte Zeile. Beim ersten Schreiben wird die Kopfzeile angelegt; danach wird jeweils eine Zeile angehängt. Teste einen falschen Wert und kontrolliere, dass die Datei unverändert bleibt. Trenne Test- und reale Daten: Starte für echte Messungen z. B. mit export COOP_DATA_FILE="$HOME/.smart-coop/stall.csv".

Dann mit dem ESP32

Starte die API für den kurzen Labortest mit flask --app sensor_api run --host PI_IP; ersetze PI_IP durch die freigegebene Projekt-IP. Die unverschlüsselte lokale API ist nur für das abgeschottete Projektnetz gedacht. Dafür müssen ESP32 und Pi laut Schul-IT miteinander sprechen dürfen. Verwende weder Debug-Modus noch Portweiterleitung.

Setze im Sketch API_URL auf http://PI_IP:5000/api/messwerte und beide Schalter auf true. Kontrolliere im Monitor HTTP 201 und suche genau diesen Messwert in der CSV-Datei. Bei Verbindungsfehlern speichert der ESP32 im Startcode keine Warteschlange; Lücken im Verlauf bleiben sichtbar.

Mit Python ein Temperaturdiagramm erstellen

Jede CSV-Zeile wird zu einem Punkt: Auf die x-Achse kommt die Empfangszeit, auf die y-Achse die Temperatur in °C. Verwende die Zeitstempel und nicht die Zeilennummer. Sonst wäre eine WLAN-Lücke im Diagramm genauso breit wie ein normaler Messabstand.

Teste diagramm.py mit der eindeutig fiktiven Beispielmessung aus fünf Messpunkten. Die Python-Datei speichert das Diagramm als PNG, auch am Pi ohne Bildschirm:

python diagramm.py beispielmessung.csv --output temperatur.png

Ersetze die Beispieldatei danach durch eine Kopie deiner echten Messreihe, etwa stall.csv. Nimm mindestens zehn Punkte auf. Prüfe beim Auswerten, ob ein scheinbarer Sprung von der Umgebung, einem Messfehler oder einer Übertragungslücke stammen könnte. Nutze auch Messfehler und Datenqualität.

Optional: Von CSV zu SQLite wechseln

Bleib bei CSV, solange eine kleine Messreihe ausreicht. SQLite lohnt sich, wenn du öfter nach Zeiträumen filtern oder viele Werte gezielt auswerten willst. Die API-Routen und das Datenformat für ESP32 und Homepage bleiben gleich; nur der Pi speichert anders.

Beende die Sensor-API vor dem Import, damit während der Umstellung keine neuen Zeilen geschrieben werden. Behalte die CSV als Sicherung. csv_nach_sqlite.py importiert nur in eine neue Zieldatei und meldet die Zahl der übernommenen Messungen.

python csv_nach_sqlite.py "$HOME/.smart-coop/stall.csv" "$HOME/.smart-coop/stall.sqlite3"
export COOP_DATA_FILE="$HOME/.smart-coop/stall.sqlite3"

Vergleiche die Anzahl mit der CSV ohne Kopfzeile. Starte die API wieder mit denselben Netzwerkeinstellungen. Prüfe zuerst GET /api/aktuell und sende dann einen neuen Messwert. Die bisherigen Reihen kannst du weiterhin mit dem CSV-Diagrammskript auswerten. Für neue SQLite-Daten braucht das Skript einen CSV-Export oder eine SQLite-Abfrage statt read_csv().

Messwerte auf der öffentlichen Homepage anzeigen

Der Pi baut die Verbindung nach außen auf und überträgt ausschließlich den letzten freigegebenen Datensatz. Der Browser fragt nur den öffentlichen Webserver ab. Es werden weder Schulnetz-Adressen noch Zugangsdaten, die CSV-Historie oder Kamerabilder über diese Schnittstelle übertragen. Gruppe B betreut den separaten Kameradatenweg.

  1. Die Lehrkraft oder Schul-IT richtet auf einem freigegebenen HTTPS-Host homepage.py, anzeige.html und messwerte.py ein. Die öffentliche App läuft hinter einem HTTPS-Reverse-Proxy mit einem WSGI-Server, z. B. waitress-serve --listen=127.0.0.1:8000 --call homepage:create_app nach Installation von Flask und Waitress. Für COOP_PUBLIC_FILE ist ein dauerhaftes, beschreibbares Verzeichnis außerhalb des Webroots nötig. Der öffentliche POST /api/publish ist token-geschützt, GET /api/aktuell absichtlich lesbar.
  2. Die Schul-IT hinterlegt auf Pi und Webserver denselben zufälligen COOP_UPLOAD_TOKEN (mindestens 32 Zeichen) als Umgebungsvariable, nie in der HTML-Seite, im Sketch oder in Git. Am Pi wird COOP_PUBLISH_URL auf die freigegebene HTTPS-Adresse mit /api/publish gesetzt. Bei Bindung der lokalen API nur an die Pi-Projekt-IP setzt du außerdem COOP_LOCAL_URL auf http://PI_IP:5000/api/aktuell.
  3. Starte am Pi python veroeffentlichen.py mit veroeffentlichen.py. Prüfe erst einen Upload, danach kann die Schul-IT den Einzelaufruf einmal pro Minute als geplanten Dienst starten. Die öffentliche App ersetzt jeweils nur den letzten Datensatz; das Programm überschreibt nicht die lokale Messreihe.
  4. Öffne die freigegebene Seite und vergleiche Temperatur, Feuchte, Lichtrohwert und Empfangszeit mit der Pi-API. Stoppe den Upload kontrolliert. Nach mehr als zwei Minuten ohne neuen Empfang zeigt die Seite den Messwert als veraltet an. Ein fehlgeschlagener Abruf wird getrennt gemeldet.

Ohne freigegebenen Host: Starte die öffentliche App zum Üben lokal mit flask --app homepage run --port 8000 und teste GET /api/aktuell. Ohne Upload-Token bleibt der Upload gesperrt. GitHub Pages kann HTML anzeigen, aber keine Flask-API ausführen. Dort kann die Anzeige bei Bedarf auf einen separat freigegebenen HTTPS-Dienst verweisen; der Beispielbrowser und seine API laufen für den einfachsten Einstieg auf derselben Domain.

Nachweise für die Übergabe

Eure Abnahme

  • Schaltskizze, kommentierter Sketch und echte serielle Ausgabe mit Einheiten.
  • HTTP-Nachweis für einen erfolgreichen und einen abgelehnten POST, dazu eine anonymisierte CSV-Probe und das Temperaturdiagramm.
  • Bei SQLite: Zahl importierter Zeilen sowie Vergleich des letzten Messwerts vor und nach der Umstellung.
  • Bei Freigabe: dieselbe Empfangszeit auf Pi und Homepage. Ohne Freigabe dokumentierst du den lokalen Funktionstest und die noch offene Veröffentlichung.

Übergebt Gruppe B das öffentliche Leseformat, die Einheiten, den Aktualitätsstatus und euren letzten nachgewiesenen Meilenstein. Dokumentiert einen Fehler und den nächsten sinnvollen Test. Die Kamera und der Messwertdienst müssen unabhängig voneinander geprüft werden können.
